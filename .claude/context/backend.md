Router: `../life-planner-back/.claude/CLAUDE.md`; full contract notes: `../life-planner-back/.claude/context/integration.md`. Read backend files only when the task needs them.

## Status

- **Supabase is the legacy backend and is being migrated to this new local backend** (`../life-planner-back`). Existing Supabase code (datasources, `@infrastructure/supabase`, `docs/database/`) stays working until each module is migrated; new work should target the new API, and for anything that needs a new Supabase table/column/policy, ask the user first whether it should go to the new backend instead.
- Migration is done module by module, swapping only the **datasource** layer (Supabase datasource → API datasource via `@infrastructure/fetcher`) while domain, use cases and presentation stay unchanged. Remove the Supabase datasource and its docs once a module is fully migrated.
- **Families and family members/invites are migrated** (specs 003, 004): the family datasource uses `GET|POST /api/v1/families` and `GET|PATCH|DELETE /api/v1/families/:familyId` (the API creates the owner's membership); the member datasource uses `GET|POST /api/v1/families/:familyId/members`, `DELETE /api/v1/family-members/:memberId`, `GET /api/v1/family-invites/:token` and `POST /api/v1/family-invites/:token/accept` (the invite token is generated by the API; never log it).
- **Auth and user are migrated** (spec 002): the app signs in with email/password through `@infrastructure/api` (`EXPO_PUBLIC_API_URL`, token in `@infrastructure/token`). Other modules still use **Supabase** data and will fail their queries until their datasources are migrated (RLS denies anonymous access). The backend currently exposes only: `GET /api/health`, `POST /api/v1/auth/login/email` (returns `{ token, refreshToken, refreshTokenExpiresIn }`, spec 027), `POST /api/v1/auth/refresh`, `POST /api/v1/auth/logout`, `POST /api/v1/auth/signup/email`, `GET /api/v1/user/me`, `GET|PATCH /api/v1/user/:id`. Authenticated calls need `Authorization: Bearer <jwt>`.
- **Account balances follow transactions** (spec 028): `GET /api/v1/finance/accounts?today=` returns `initialBalance`, `balance` (current) and `projectedBalance` (end of month); create takes `initialBalance` (a `balance` field is a 400); the balance of an existing account changes only through `POST /api/v1/finance/accounts/:id/balance-adjustment` (an INCOME/EXPENSE transaction on the system category `BALANCE_ADJUSTMENT`, listed with `category.systemKey` and excluded from totals); 422 on archived accounts.
- **Archived sources on the dashboard** (spec 052): account and card responses gain `archivedAt: string | null`. `/finance/dashboard/summary|balance-series|totals` count an archived account in a day's balance only before its archive day (São Paulo calendar day of `archivedAt`), and a transaction only if dated before the archive day of its account (card rows: of its card); reactivating restores everything. Nothing else (Accounts, Transactions list, daily balances) changes; the frontend needs no change to keep working.
- **Credit cards** (spec 026): `GET|POST /api/v1/finance/credit-cards`, `GET /overview` (computed invoices, limit aggregate; "today" is America/Sao_Paulo), `GET|PATCH|DELETE …/:id`; cents end to end, repeated `ownerId` and `status` query params, PATCH `null` clears `paymentDay`/`lastDigits`; delete is 409 once the card has purchases.
- **Card purchases and invoice payment** (spec 029): `POST|PATCH /finance/transactions` take `accountId` XOR `creditCardId` (card purchases are EXPENSE, response adds `creditCard`, `invoiceMonth`, `overLimit`); `GET /finance/transactions` returns account rows only unless `?source=CARD`; `GET /finance/credit-cards/invoices?month=YYYY-MM&ownerId&today` (invoices whose list day is in the month, with purchases), `GET …/:id/invoices/:month`, `POST …/:id/invoices/:month/payment` (`{method: ACCOUNT|EXTERNAL, accountId?, paidOn?}`), `DELETE …/payment`; the overview adds `upcomingInvoices`, `listDate`, `payment`. 422 `Invoice is paid` / `Credit card is archived` / `Use the invoice to change this payment`; 409 `Invoice already paid`.
- **Financial is fully migrated** (spec 006): `GET|POST /api/v1/finance/{accounts,categories,transactions}` and `PATCH|DELETE …/:id`; money travels as integer cents (the models convert), ownership (USER/FAMILY) is enforced by the API and list calls pass repeated `ownerId` params.
- **Stock is migrated** (spec 005): `GET|POST /api/v1/stock/items` and `GET|PATCH|DELETE …/:id`; the API enforces USER/FAMILY ownership (404 for items of others, 403 for a forbidden owner) and the stock datasource lives in `src/data/datasource/data/storage/items/api/`.
- Swagger (when the backend runs): `/swagger`; base path `/api/v1`.

## Rules when touching the API contract

- New data/behavior needed by the app → check the backend endpoint table (`../life-planner-back/.claude/context/api.md`) first; if it's missing, tell the user the backend needs it (don't invent endpoints).
- Keep enum values (`USER`/`FAMILY`, …) and UUID ids identical to the backend. API JSON is camelCase.
- When integrating, follow the existing layering: a new datasource under `src/data/datasource` using `@infrastructure/fetcher` (never call `fetch`/axios from presentation), Model `fromJSON/toJSON`, repository impl, use case. The base URL comes from an `EXPO_PUBLIC_*` env var (placeholder in `.env.example`; never a real URL/secret in tracked files).
- Don't edit the backend repo unless asked; report what must change there.

## Recurring transactions (spec 034)

`/v1/finance/recurrences/*` (create, list, get, patch = scope ALL, `split` = THIS_AND_NEXT, `occurrences/:number` = make a projected occurrence real, delete by occurrence or whole series, `projections?from=&to=`). `PATCH`/`DELETE /v1/finance/transactions/:id` on a recurring row need `scope` (paying needs none). Transaction payloads carry `recurrenceId`, `occurrenceNumber`, `occurrenceCount`, `recurrenceFrequency`. Every read of rows (list, accounts, cards, invoices, projections) makes the API create the real occurrences up to the end of the client's current month (`?today=`), so the app always sends its local day. 409 on a delete answers `{ paidCount, paidTotal, detachedCount }` (the app keeps only the numbers, see `ApiBusinessError.details`).

- **Categories for all scopes** (spec 038): category create takes `owner: "ALL"` (no `ownerId`), PATCH takes `scope: "ALL"`; the output has `scope` (`PERSONAL | FAMILY | ALL`) and `scopes` (the ones the caller reaches). `GET /finance/categories` returns an All category once. Delete is 409 while any scope uses it.
- **Archived categories** (spec 041): the category output has `status` (`ACTIVE | ARCHIVED`, a missing value reads as `ACTIVE`); `PATCH /finance/categories/:id` takes `status` and applies it to the whole subtree. Archiving answers `409` with `blockers` (`recurrences`, `installmentPlans`) and an optional `hiddenCount` while recurrences or running installment plans use the category (`ApiBusinessError.body` carries it; `updateCategory` maps it to `CategoryHasPendingItems`). New 422s: `Category is archived` (`CategoryArchived`) and `Parent category is archived` (`CategoryParentArchived`). Archived categories stay in the list; the app hides them from pickers (`selectableCategories`) except the one already selected.

## Currency per resource (spec 040)

Accounts, cards, transactions, recurrences, projections, installment plans and invoices come with `currency` (`BRL | USD | EUR`, default `BRL`). `toCurrencyCode` (`@domain/entities/financial/Currency`) reads it in every model and falls back to `BRL` for an older API, so the cache and the screens never see `undefined`. The app never sends `currency` on create (the API takes the account's or card's); a transaction in another currency than its account is a 422 the app cannot produce today. Invoice payment / early payment / card `paymentAccountId` across currencies is also a 422.

- **Archived families** (spec 042): `FamilyOutput.status` (`ACTIVE | ARCHIVED`, a missing value reads as `ACTIVE`); `PATCH /families/:id` takes `{ status }` alone. Archiving answers `409 "Family has pending items"` with `blockers` (`recurrences`, `installmentPlans`, `invoices`, `unpaidTransactions`, `pendingInvites`; money in cents) and `counts`; the datasource maps it to `FamilyHasPendingItems`. Every write on an archived family answers `422 "Family is archived"` (`FamilyArchived`). Lists without an explicit owner skip archived families; the app sends explicit owner ids and filters archived ones client-side ("All" = active owners, an archived family only when selected).

## Tags (spec 043)

`/v1/finance/tags` (`GET ?ownerId`, `POST { name, owner: USER|FAMILY|ALL, ownerId? }`, `PATCH { name?, scope: "ALL" }`, `DELETE`; 409 = name in use, ignoring case). Transactions, installment plans and recurrences take `tags: string[]` (names, max 10 x 30 characters; omitted = unchanged, `[]` = remove all) and return `tags: [{ id, name }]`; the API resolves or creates the names in the owner of the record. The app reads the tags of all owners once (`CACHE_FINANCIAL_TAG_DATA`, invalidated by every transaction/plan/recurrence write) and filters them per owner for the suggestions.

- **Transaction filters** (spec 045, additive): optional `from`+`to` (up to 2 years), `q`, `categoryId` (descendants included), `tagId`, `accountId`, `creditCardId`, `paid` on `GET /finance/transactions`; `/credit-cards/invoices` also takes `from`/`to` instead of `month` and returns `filteredTotal`/`matchedCount`/`purchaseCount` per invoice; `/recurrences/projections` takes `q`, `categoryId`, `tagId`, `accountId`, `creditCardId`. The app sends them through `appendFilterParams`.

## Transactions CSV (spec 047, additive)

`GET /v1/finance/transactions/export` (`text/csv`, attachment; query `from`, `to`, `owner=ALL|USER|FAMILY`, `ownerId`, repeated `accountId`/`creditCardId`, `format=BR|INTL`, `lang`; the app reads the filename from `Content-Disposition` through `api.getText`), `GET /export/count` (`{ count }`) and `POST /import` (`{ owner, ownerId, dryRun, rows[] }`; a dry run answers `200 { errors, duplicates }`, the real run `201 { created }`, and a refused file `422 { errors: [{ line, code, message }] }` which `importTransactions` maps to `ImportRowsInvalid`). Money in the rows is integer cents. The app sends `today` so account rows default to paid by the client's day.

Spec 048 (additive): import rows may carry `invoiceMonth` (`YYYY-MM`) and `paidFromAccountId`; `categoryId` may be `CARD_REFUND`, `INSTALLMENT_PREPAYMENT_DISCOUNT`, `CARD_EARLY_PAYMENT` or `INVOICE_PAYMENT`; error lines may carry `params`; the dry run answers `invoices: [{ creditCardId, invoiceMonth, amountDue, paid }]`; new error codes `CARD_INCOME_CATEGORY`, `CARD_CREDIT_CATEGORY_MISUSED`, `INVOICE_MONTH_INVALID`, `INVOICE_PAID`, `INVOICE_NOT_CLOSED`, `INVOICE_ALREADY_PAID`, `DUPLICATE_INVOICE_PAYMENT`, `INVOICE_PAYMENT_MISMATCH`, `EARLY_PAYMENT_OVER_DUE`, `PAID_FROM_ACCOUNT_INVALID` (`CARD_CREDIT_NOT_SUPPORTED` is gone).

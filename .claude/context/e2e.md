# E2E (Maestro, web)

One suite guards both repos. The flows live **only** here (`e2e/`); the backend's `yarn e2e` forwards to this repo's runner. The suite runs against the current working trees of both repos, because the owner keeps `yarn web` (here) and `yarn start:dev` (`../life-planner-back`) running in watch mode on the Mac.

## Layout

```
e2e/
  config.yaml      workspace config
  flows/<module>/  one folder per module (auth, account, financial/*, stock, family)
  subflows/        signup-via-api.yaml (fresh user; outputs EMAIL, PASSWORD, TOKEN, REFRESH_TOKEN, USER_ID), login-by-token.yaml (default login: TOKEN/REFRESH_TOKEN through the dev-only `/e2e-login` route), login.yaml (UI login with EMAIL/PASSWORD, only for flows that test the login screen: `flows/auth/`),
                   setup/create-<resource>.yaml (API setup; also create-family, create-extra-user, add-joined-member), family/open-family.yaml, stock/open-stock.yaml, financial/open-accounts.yaml, financial/open-categories.yaml, financial/open-transactions.yaml, financial/scroll-form-down.yaml
  scripts/         copy-user.js (save/restore the current user under a prefix), unique-user.js, api.js, random-name.js (output[KEY] = "<PREFIX> <4 digits>"), setup/create-<resource>.js
scripts/e2e/       run.mjs + cli.mjs (runner), summarize.mjs (report), unit tested
e2e-report/        generated, gitignored
```

## Running

- `yarn e2e --list-tags` (or `yarn e2e:tags`) lists every tag with its flow count; it only reads `e2e/flows`, so it needs no Maestro, API or app.
- `yarn e2e` runs the flows in `E2E_WORKERS` parallel Maestro processes (default 6, `--workers <n>`; `--workers 1` = one process). Flows that fail get one retry pass at 3 workers; the summary reports `retry at 3 workers: N/M passed` (retry output: `junit-x<n>.xml`, `maestro-x<n>.log`, `artifacts/x<n>/`). The runner splits flow files by last known duration (`e2e/.durations.json`, gitignored), writes `e2e-report/junit-w<n>.xml`, `maestro-w<n>.log`, `artifacts/w<n>/` and merges them into the usual `summary.md` / `failed.txt`. Full suite 13m44s with 3 workers (6 workers: 7m44s).
- `yarn e2e --changed` runs only the flows the changed files can break (both repos; `--dry-run` prints the selection without running; mapping in `scripts/e2e/impact.mjs`; `--tags` wins over `--changed`). Docs-only changes print `E2E SKIPPED` and exit 0. `yarn e2e --unchanged` is the complement: it runs only the flows `--changed` did not select (same selection, same `--dry-run`), so `--changed` green + `--unchanged` green covers the full suite without running any flow twice; it prints `E2E SKIPPED` when `--changed` already selected everything.
- `EXPO_PUBLIC_E2E_LOGIN=true` in `.env` (and a restart of `yarn web`) is required for token login; without it the route redirects to the login screen and flows fail at `login-by-token`.
- `yarn e2e` whole suite, `yarn e2e --tags <tag>`, `yarn e2e:smoke`, `yarn e2e:failed` (only the flows in `e2e-report/failed.txt`).
- By default the Chromium window is visible; `--headless` hides it and combines with the other flags (`yarn e2e --headless --tags auth`). AI sessions use `--headless` so no window pops up on the owner's Mac.
- In a terminal (TTY) the runner shows live progress (`scripts/e2e/progress.mjs`): every flow as ✔ passed (duration) / ✖ failed / ▶ running / · pending, redrawn each second. AI shells and CI are not a TTY, so they only get the final summary.
- Needs Maestro and `E2E_ENABLED=true` in the gitignored `.env` (Mac only). The runner never starts, builds or stops the app or the API.
- Exit codes: 0 all passed, 1 a flow failed, 2 could not run (guard, Maestro, API or app missing, no report). Exit 2 means **not validated**.

## Reading the report

Open only `e2e-report/summary.md` (it is also what the command prints):

- Passed: one line `E2E PASSED: N/N flows (<duration>) · app <branch>@<sha> · api <branch>@<sha>`.
- Failed: a header and one block per failed flow (flow name and tags, flow file, step, error, screenshot, log), at most 15 blocks then `+N more failed flows`.
- `LIKELY ENVIRONMENT FAILURE` (more than half failed): check the app, the API and the login flow first; only 3 blocks are shown.
- Open only the files named in a failure block; never the log or artifacts of passing flows.

## Writing a flow

- Header: `url: ${E2E_WEB_URL}` and first step `- launchApp: { clearState: true }`, `name:` equal to the path under `flows/` without extension, `tags:` in list form (one **primary** module tag (the folder; other module tags are allowed on cross-module flows), `spec-NNN`, `smoke` on 1–2 flows per module, `wip` only while building).
- Create the user with `runFlow: ../../subflows/signup-via-api.yaml`; it exposes `${output.EMAIL}`, `${output.PASSWORD}`, `${output.TOKEN}`. Set up data through the API, drive only the behavior under test through the UI.
- Select by `id` only (testIDs), never by visible text. No fixed sleeps: `extendedWaitUntil`.
- One behavior per flow; each flow must pass alone and in any order.

## testIDs

Format `<module>.<screen>.<element>` in kebab-case, defined in the screen folder's `testIds.ts` (for example `Login/testIds.ts`) and used by the View, its Jest tests and the flows. `@components` that wrap RN elements forward `testID` (and derive `-error`, `-toggle`, `-frame` suffixes for `TextField`).

Forms on the web suite are two-column (spec 037): `FormColumns` derives `<sheet testID>-column-left` / `-column-right`, and the Delete button of edit forms sits in the sheet footer (`<sheet testID>-footer`) with its id unchanged.

A wrapped component that takes an `accessibilityLabel` must also set `nativeID={testID}` (Maestro web resolves `id` before `data-testid`; `Touchable` and `TextField` already do).

Maestro facts verified on this Mac (flags, JUnit mapping, `id` matching on web) are recorded in `e2e/README.md`.

## Setup through the API (spec 018)

Data that is not under test is created through the API, never the UI. One self-contained GraalJS script per resource in `e2e/scripts/setup/` (no imports) reads `E2E_API_URL` (already ends in `/api`), `TOKEN` and its params from `env`, calls the endpoint with `Authorization: Bearer`, throws `E2E setup: <resource> failed with status <n>` on non-2xx and writes the id to `output` (`ACCOUNT_ID`, `CATEGORY_ID`, `TRANSACTION_ID`). A thin subflow in `e2e/subflows/setup/` passes the params and holds defaults in its header `env:`. Existing: `create-account`, `create-category`, `create-transaction`. USER-owned records use `OWNER_ID: ${output.USER_ID}`. Names typed or created by flows use `random-name.js`. When two setup calls output different ids, copy the first one right away (`- evalScript: ${output.KEEP_ACCOUNT_ID = output.ACCOUNT_ID}`) only if a later script reuses the same key.

Maestro web facts from spec 018: the form sheet does not scroll with `scrollUntilVisible` or a center swipe, use `subflows/financial/scroll-form-down.yaml` (swipes with explicit coordinates); elements outside the viewport are not found. `AmountInput` keeps the typed digits after the current ones, so `eraseText` before `inputText` (digits only: `123456` shows `$1,234.56`; assert with a locale-tolerant regex like `.*1[.,]234[.,]56.*`). An `id` is a regex, so `a|b` matches either. Derived ids: `<id>-error` (FieldShell), `<id>-icon-<value>` (IconChoiceGroup), `<id>-confirm` (ConfirmDialog), `<id>-close` (BottomSheet), `<id>-title` / `-balance` (ListItem rows). Components that take an `accessibilityLabel` must set `nativeID` (SegmentedControl and AmountInput were fixed in 018).

Accounts (spec 028): `BALANCE_CENTS` is the INITIAL balance and, with `STATUS` and `OWNER`, a caller-scoped param read by `create-account.js` (never a header default). `scripts/future-date.js` outputs `NEXT_MONTH_DATE` and `LATER_THIS_MONTH_DATE` (empty on the last day of the month): flows that depend on a date later this month guard it with `runFlow: when: true: ${output.LATER_THIS_MONTH_DATE != ''}`.

Categories (spec 019): `create-category` also nests a category when the caller passes `PARENT_ID` (a caller-scoped variable the script reads if defined; do not declare it in the subflow header or the runScript env, Maestro dropped it there). Keep the parent id under another key (`PARENT_CATEGORY_ID`). More derived ids: `<id>-EXPENSE` / `<id>-INCOME` (SegmentedControl appends the uppercase option value), `<id>-option-<value>` (SelectField, value = category id), `<id>-swatch-<hex>` (ColorSwatchGroup), `financial.category-form.name-preview` (typed name heading, use it to assert a saved name since Maestro web matches text, not input values). The list plus button does not pass the current type to the form, so flows pick the type in the form.

Transactions (spec 020): `subflows/setup/finance-basics.yaml` creates one account plus an EXPENSE and an INCOME category (inputs `TOKEN`, `OWNER_ID`; outputs `ACCOUNT_ID`, `ACCOUNT_NAME`, `EXPENSE_CATEGORY_ID/NAME`, `INCOME_CATEGORY_ID/NAME`). `create-transaction` takes `DESCRIPTION`, `VALUE_CENTS`, `DATE` (explicit) or `MONTHS_AGO` (`0` = today by the local date, `n` = the 10th of the month n months ago), `TYPE`, `OWNER`; these optional params are read by the script and must **not** be header defaults, because Maestro keeps the header default over the caller value (also true of `TYPE` in `create-category`). `assertNotVisible` with only a `text:` regex matched on web although the text was not on screen: scope it with an `id` (for example `financial.transactions.summary-expense`) and pair it with a positive assertion on the same id. Quick add is `quick-add-button|navigation-rail-add` (the wide layout shows the rail button).

Stock (spec 021): `create-stock-item` takes `DESCRIPTION`, `QUANTITY`, `UNIT` (`gram|kilogram|liter|milliliter|unit`), `EXPIRATION_IN_DAYS` (absent = none, negative = expired, `0` = today; the script adds N × 24 h to now) and `OWNER`; read by the script, not header defaults. Output `STOCK_ITEM_ID`. The "expiring" window is 7 calendar days (`CLOSE_TO_EXPIRATION_DAYS`) and the EXPIRING filter includes expired items; Home's stock card links to `/stock?filter=EXPIRING`. The app has no out-of-stock status (a quantity-0 item is a plain row). List rows share `stock.list.row` (title `-title`; quantity `stock.list.row-quantity`, shown only when the row has no badge; badges `stock.list.status-expired|expiring`); chips are `stock.list.filter-<ALL|EXPIRING|EXPIRED|PERSONAL>`; unit options `stock.item-form.unit-select-option-<unit>`; details brand `stock.item-details.brand-value`; Home card `home.stock-attention.*`. `SearchField` needed `nativeID` for Maestro web. The expiration date picker (`react-native-paper-dates`) has no ids on its day cells or Save button, so flows set expiration dates through the API only.

Family (spec 022): `setup/create-family` (`TOKEN`, `NAME` → `FAMILY_ID`, which is also the `OWNER_ID` of the family's records). `OWNER: FAMILY` is a caller-scoped param of `create-account`, `create-category`, `create-transaction` and `create-stock-item` (the first two had `OWNER: USER` as a header default, removed; scripts default to `USER`). Call these subflows directly from the flow, not through another subflow. Extra users: `setup/create-extra-user` (env `PREFIX`, for example `MEMBER_`) stores `<PREFIX>EMAIL|PASSWORD|TOKEN|REFRESH_TOKEN|USER_ID` and restores the main user's keys (`scripts/copy-user.js`); `setup/add-joined-member` (env `FAMILY_ID`) creates user B and runs `scripts/setup/join-family.js`, where the owner invites and B accepts in one script so the invite token never reaches env, output or logs. Switching user mid-flow: `launchApp: { clearState: true }` then `subflows/login-by-token.yaml` (with the prefixed `TOKEN`/`REFRESH_TOKEN`) works on web. Owner chips: `<form id>-<ownerId>` (family chip = `-${FAMILY_ID}`, personal chip = `-${USER_ID}`); in the account form they sit below the fold (`scroll-form-down` first). The transaction form puts the owner chips last and a change resets category and account: scroll down, pick the owner, `scroll-form-up`, pick the category, scroll down, pick the account. Family list ids carry the id (`family.card.title-<familyId>`); flows that create the family in the UI match with `.*`. Maestro is installed in `~/.maestro/bin`: add it to `PATH` in a shell that does not load the profile.

Account deletion (spec 024): flows in `flows/account/` (tags `account`, `spec-024`). Assertions against the API live in `scripts/assert/*.js` with thin subflows in `subflows/assert/` (`assert-login-fails` / `assert-login-works` take `EMAIL`/`PASSWORD`; `assert-token-rejected` takes `TOKEN`; `assert-family-member-absent` takes `TOKEN`, `FAMILY_ID`, `EMAIL`; `assert-delete-other-user-rejected` takes `TOKEN`, `VICTIM_EMAIL` and sends `DELETE /v1/user/me` with a body through `http.request`). `subflows/account/open-settings.yaml` goes Home → profile button (`home-profile-button`) → Settings. ids: `settings.delete-account.button|confirm-dialog(-confirm|-cancel|-message)|email-sheet|email-input|submit-button|cancel-button|error`, `auth.login.account-deleted-notice`. Deleting the user mid-flow means the next login in the same flow needs `launchApp: { clearState: true }`; a deleted user's token and credentials are asserted dead through the API, not the UI. Maestro web does not expose a disabled button (`assertVisible: enabled: false` never matches): assert that pressing it changes nothing. `POST /v1/auth/login/email` answers 201, so "login works" asserts 2xx.

Teardown (after spec 024): every flow declares `onFlowComplete: - runFlow: <depth>/subflows/cleanup/delete-e2e-users.yaml` in its header (new flows must too). It runs `scripts/cleanup/delete-e2e-users.js`, which logs in with the flow's `EMAIL`/`PASSWORD` (and `MEMBER_`, `OTHER_`, `STRANGER_` extra users) and calls `DELETE /v1/user/me`, removing the users and their data even when the flow failed. It only touches emails shaped `e2e+<suffix>@example.com`, skips users that are already gone and never fails the flow. A new extra-user prefix must be added to the `prefixes` list in the script.

Recurring transactions (spec 034): `setup/create-recurrence` (`DESCRIPTION`, `VALUE_CENTS`, `FREQUENCY`, `MONTHS_AGO` (`0` = starts today, `n` = the 10th of n months ago), `END_MONTHS_AFTER_START`, `PAID`, `TYPE`, `OWNER` read by the script; output `RECURRENCE_ID`) creates a series through the API: the API makes the real occurrences up to the end of the month and projects the rest. A recurring row's title id is `financial.transactions.row-recurring-title` (projected: `row-projected-title`), not the shared `row-title`. The end-date picker has no ids, so flows never set an end date through the form.

Finances sections (spec 044): the segmented control is gone. The E2E runs on wide web, so the `subflows/financial/open-*.yaml` subflows and flows switch sections with the rail children `navigation-rail-financial-<transactions|categories|tags|accounts|cards>` (visible only inside Finances). Mobile ids: `financial.layout.section-picker` (title button, suffix `-title-button`), `financial.layout.section-sheet`, `financial.layout.section-sheet-<section>`. Flow: `flows/navigation/finances-sections.yaml` (tag `navigation`).

Transaction filters (spec 045): ids `financial.transactions.search`, `filters-button` (badge `filters-button-badge`), `active-filter-<group>` (`-remove`), `clear-filters`, `period-chip`, `filtered-summary`, `filters-empty` (`-action`), `cardInvoice.match`; modal `filters-sheet`, `filters.apply|cancel|clear|done|back`, `filters.period-mode-<THIS_MONTH|LAST_3_MONTHS|THIS_YEAR|CUSTOM>`, `filters.origin-option-<ACCOUNT|CARD>`, `filters.situation-option-<PAID|UNPAID>`, `filters.category-<id>`, `filters.source-<id>`, `filters.period-error`. The wide modal does not fit the 1024x625 viewport: `scroll-form-down` before the Situation chips. `create-card-purchase` takes optional `SECOND_CATEGORY_ID`, `SECOND_DESCRIPTION`, `SECOND_VALUE_CENTS` (a second purchase on the same invoice). Flows: `flows/financial/transactions/filters-category-period.yaml`, `filters-empty-state.yaml`.

Overview (spec 046): testIDs in `Financial/Overview/testIds.ts` (`financial.overview.screen`, `tile-<balance|income|expense|result>`, `balance-chart`, `income-expense-chart`, `categories`, `category-row-<id>`, `tags`, `tag-row-<id>`, `scope-<id>`, `period-<12M|3M|6M|YEAR|CUSTOM>`, `granularity-<DAY|WEEK|MONTH>`, `currency`, `filters-button`, `empty`, `custom-*`). Maestro web only finds elements in the viewport and the page scrolls with `subflows/financial/scroll-list-down.yaml` (`scrollUntilVisible` does not scroll it). A component with an `accessibilityLabel` must set `nativeID` (`StatTile` does). Flow `financial/overview/open-overview-and-drill`; `navigation/finances-sections` also visits the Overview. `takeScreenshot` needs a relative name (it writes under `e2e-report/artifacts/<run>/<flow>/takeScreenshot/`).
